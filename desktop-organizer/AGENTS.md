# Codex 项目强制开发规则：曲谱库·重奏乐谱整理工具（Windows V1）

> 生效范围：本仓库全部代码、测试、文档和打包操作。产品细则见 `SPEC.md`；工作进展见 `PROGRESS.md`。
> **优先级：数据安全与正确性 > 验收通过 > 范围控制 > Token 节约 > 开发速度。**

## 1. 只在同一个 Work 开发（硬约束）
- 在用户指定的**同一个 Codex Work / 当前会话工作区 / 同一仓库的当前工作目录**持续开发和修复；不要新建其他 Work、任务、项目、仓库、分支、worktree 或并行子代理来分散本项目。
- 如果当前平台自动隔离任务或无法继续原 Work，先清楚说明限制；不要悄悄在别的空间重头做。不能以“分工更快”为由绕过本条。
- 每次开始先读取 `PROGRESS.md` 的简短状态，检查当前代码和必要的 `SPEC.md` 小节；**续做已有成果，绝不从零重构**。
- 除非用户要求，不创建 PR、不推送远程、不做 git commit，不更改主曲谱管理系统仓库。所有开发只作用于本项目。

## 2. 不能为了交工而交工（硬约束）
- 不以“代码写完”“页面能打开”“我认为没问题”作为完成标准；必须达到 `SPEC.md` 的对应验收条件。
- **每完成一个可独立验证的设计/模块/修复，立即检验**：需求对照 → 相关自动化测试 → 必要的界面或文件输出实际验证 → 记录结果。失败先修复、复测，再进入下一模块。
- 不允许虚构测试结果、编造成功日志、删除失败测试、通过跳过测试掩盖缺陷，也不能用写死的演示数据代替真实功能。
- 启动相关自动化必须隔离默认数据库与迁移/扩位启动记录：整轮设置 `SCORE_ORGANIZER_DATA_DIR`、`SCORE_ORGANIZER_EXPANDED_PROFILE` 到测试临时目录；直接调用启动函数的测试也须使用自己的临时启动目录，不能仅读取/替换默认数据库路径而遗漏用户现有迁移指针。不得让自动化进入用户实际曲库。
- 无法执行 Windows GUI/打包测试时，明确标注“未在 Windows 验证”，留下可重复执行的验证步骤；不得声称已交付 Windows 成品。
- 遇到编号错配、PDF丢失、静默覆盖或两套目录不一致，视为**阻断问题**；修复前不得发布或继续依赖该功能。
- 不擅自改动用户既有编号、不自动合并疑似同曲、不自动判定第二版、不覆盖原始PDF。

## 3. 极致节约 Token，但不牺牲质量（硬约束）
- **先定位、后读取**：使用 `rg` / 定向文件查看 / 小范围 diff；不反复全文读取规范、大文件或仓库，不输出大量文件全文与长日志。
- 仅查看当前任务直接相关的源文件和 `SPEC.md` 章节；避免重复解释已确定规则。所有关键决定写入 `PROGRESS.md`（短摘要）以便继续同一 Work。
- 一次聚焦**一个最小可验收模块**；优先改现有代码、复用现有函数，避免重复实现、过度封装、无关重构和多余依赖。
- 调用工具时尽量组合相关的简短命令；先运行相关小范围测试，阶段末再运行完整回归测试。输出测试**摘要及失败关键信息**，不回显海量通过日志。
- 不要为节省 Token 省略验证、边界检查、备份、安全措施；不通过“减少必要测试”来假省成本。
- 汇报一律简短：`完成内容 / 验证（通过、失败、未测） / 风险或阻断 / 下一步`；每项1～3行，不写冗长过程叙述。
- 问题只有在**规范有冲突、存在无法逆转的数据风险或缺少不可推断的关键输入**时才问用户；其余自行按现有规则落地并测试。禁止反复问已回答的问题。

## 4. 产品范围与硬规则
- 产品是**Windows 10/11 本地离线桌面软件**，处理重奏 PDF 分谱；不做云端/NAS、登录、AI、OCR、PDF内容解析、乐谱编辑。
- 识别只依赖**文件名编号**：旧文件名 `乐器2位+自定义分类2位+曲名.pdf`；新分谱名 `乐器2位+分类2位+曲目序号3位+曲名.pdf`（用户再次确认）。先尝试完整识别新格式，再识别旧格式；不合法/无编号进入人工补录。
- 第二组分类不是“作曲家”字段，是用户定义的**分类/风格**（例：久石让、迪士尼、中国风格）；不可硬编码作曲家语义。
- 曲目文件夹 `分类2位+序号3位+标准曲名+（独立乐器数量2位）`，例如 `01001天空之城（07）`；分谱如 `0101001天空之城.pdf`。
- 普通完整重奏默认至少 **3种不同乐器**（可按分类配置）；不足时正常入库保留待补齐草稿，也可选择独立“待审查”，不占正式流水。用户最新明确要求：**强制正式入库允许只有一个声部**，须明确选择分谱、预览并勾选确认；只豁免该曲目的最少声部数，持久记录与审计，后续补谱沿用原号，不改变其他曲目默认规则。正式编号、双目录与真实乐器计数仍正常生效，重复/命名/文件安全不豁免。相同乐器多份PDF只算一种；待审查仍按原因保存说明，可放回草稿。
- 用户确认重复的草稿分谱，先复制到独立“已确认重复”目录并核对哈希，保留确认说明和对比文件记录，成功后再移出草稿；失败保留草稿。原始PDF和库内文件保留，不静默决定重复取舍。
- 用户可主动修改已入库曲目的曲名及分类：必须预览、备份、同步两套输出和数据库，失败回滚；原序号、版本身份和原始PDF保持不变，不自动合并同名曲目。此项为用户明确确认的目录编辑，不等同于新增版本时修改原版。
- 已入库同分类、同版本且同名或仅空格不同的误拆曲目可人工确认合并：用户选择保留的已有编号，同乐器分谱逐份对比并确认保留/重复转存，预览和备份后同步双目录与数据库。另一编号保留merged占号记录，不再显示独立正式曲目；原始PDF不变，失败回退。不提供任意改流水，不自动合并或判定重复/版本。
- 用户明确确认“清空全部整理数据”时，先备份数据库并将程序整理目录转入清空备份，再清除库记录；原始PDF、分类和乐器配置保留。此时为新空库，从001开始；普通清草稿或编辑不可据此重用编号。恢复旧库不得覆盖新数据，失败须回退或明确阻断。
- **单版本不标版本**；确认第二版时分配全新序号并加 `（第二版）`，第三版同理；不修改原版已入库编号与路径。
- 双目录：`按乐器分类/`、`按曲目分类/`；两边都生成可打开的独立 PDF 文件；原始文件永不就地重命名/覆盖。
- 固定预警与人工校对区必须支持：编号无效、疑似同曲、分类冲突、同乐器多文件/不同版本、重复文件、乐器不足、命名或覆盖冲突，能定位文件并手改后重新校验。
- 每首曲目归档前必须展示曲目信息及全部分谱的**原名→新名表格**；批次结束展示总表。
- **用户已最终确定全库统一流水**：曲目三位序号 `001…999` 在所有自定义分类之间唯一（包括同名的不同版本）；数据库对正式序号设置全局唯一约束。2026-10-18用户更新分配规则：已有编号保持，新曲优先使用全库真正未占用的最小空号；所有状态的曲目、merged历史与本批显式编号继续占号，预览和实际归档均逐个跳过占号。不得按分类重新分配，不提供编号作用域选择界面，不改既有编号或原PDF。此项覆盖旧最大值+1规则；未开放扩位候选的激活策略另行验证，不能据此开放1000以上。

## 5. 技术、流程和交付
- 优先采用 Python + PySide6 + SQLite + RapidFuzz + pytest + PyInstaller，保持可离线运行、中文路径正常、依赖少；不擅自换技术栈。
- SQLite 保存自定义分类、乐器、曲目、版本、编号、PDF哈希、别名、预警处理、导入历史；输出前做冲突检查，支持恢复和幂等重试。
- 每次归档必须先生成预览方案，暂存输出、验证完整性，再提交两套目录与数据库状态；失败后需能恢复/明确提示，不能宣布成功。
- 按 `SPEC.md` 的里程碑顺序推进；不跳阶段，不扩需求。更新 `PROGRESS.md` 的“已完成、通过的测试、当前阻断、下一步”四项。
- **交付必须包含**：可运行源码、真实自动化测试、Windows启动与打包方法、Windows可执行程序或明确的未验证说明、测试结果与已知限制。不要以空壳原型冒充成品。

## 6. 每次任务结束前的自查（必须执行）
1. 本次变更是否严格符合现有命名、版本和人工预警规则？
2. 是否运行了相关测试，且结果如实记录？涉及文件写入时是否验证原件未变、两套目录一致？
3. 是否误开新 Work/分支，是否引入无关重构或无用输出？
4. 是否更新简短 `PROGRESS.md`，使下一次能直接继续？
5. 是否明确区分“已实现且验证”“已实现但未验证”“未实现”？
