## 已实现的边界

`expanded_candidate.prepare_candidate`只接收现有完整备份和全新目标目录。先用既有验证/独立恢复流程得到临时副本，要求数据库2，检查已有乐谱元数据、排队上传及冻结乐谱中的编号。遇到未支持历史值直接停止，原备份、原库和原PDF不重编号、不覆盖。候选保留业务表、账号/团队/乐谱UUID、授权、节目单及冻结内容；恢复副本中的会话和邀请按既有安全规则清除。

仅在临时副本增加命名版本、候选存储ID及绑定路径三个元数据值，并设置数据库3。全新目标先收到库3文件，随后复制PDF并逐份核对独立副本哈希；原备份SHA在恢复和复制后再次核验。完成标记先写入私有pending文件并fsync，再独占建立正式文件名、移除pending链接。中途复制、哈希核验、标记发布或链接移除失败时，目标保持不可打开，不自动清理或复用失败目录。

`ExpandedCandidateService`继承既有账号验证逻辑，不调用普通服务的建库/迁移构造器。每次连接和提交前核对库3、命名2、目录/存储身份和硬链接；绑定标记不允许额外字段、重复JSON字段或布尔版本值。缺失数据库不会重新创建，运行期间标记或库版本被改变会回滚本次业务写入。复制目录到其他路径也不能自动重绑定。

普通服务仍拒绝库3。本轮同时在独立本地Python进程运行18封存源码中的旧账号服务，确认其返回unsupported_database，业务行和旧源码文件保持。此项不是旧EXE、NAS容器或旧进程操作系统隔离验收。
