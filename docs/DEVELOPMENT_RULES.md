# 开发与阶段审查规则

## 硬规则

1. 基于既有工程继续，不重建，不绕过 Domain。sources/ 只读，用户既有改动不撤销。
2. 发现问题不是报告终点：先修复 → 重测 → 再审查；存在结构性阻塞时不能宣布通过。
3. 不能假称执行、构建、测试、真机验证或同步已完成。不可行项明确记录证据与限制。
4. 修改数据库必须导出 schema，实际测试升级和数据保留；禁止破坏性迁移和悄悄重置数据。
5. 不自动扩大授权，不静默读错谱/旧版本/其他成员数据，不把 UI 判断当安全边界。
6. 保持本阶段范围，不提前塞入 NAS、阿里云、多租户、商业运营或下一阶段具体实现。

## 验证要求

实际运行 Gradle APK 构建、测试、Lint；依风险追加 Domain、Room、ViewModel、Compose 和真实 Android 集成测试。记录精确测试数量、失败/跳过、工具/设备和报告位置。

PDF/坐标/交互检查必须使用真实 PDF，不用占位图假装渲染通过。普通/大 Pad 截图检查非空、清晰、无覆盖、布局合理。模拟器、Preview、JVM 截图和真机须明确区分。

审查重点：授权泄露、版本与页段、状态错误、取消/并发、配置变化、导航栈、内存性能、后续边界与迁移。发现缺陷修复后重跑受影响测试和完整回归。

## 文档交付

持续使用当前固定 Work。每个阶段维护 docs/PROJECT_STATE、PHASE_HISTORY 和 PHASEx_REVIEW；有新产品决策则更新其唯一所属规范，其他文档链接引用，不复制多份需求。

阶段报告包括：范围、实际改动、发现并修复的问题、测试数量、Build/Lint 结果、证据路径、未验证项、非阻塞风险、阶段结论及是否可进入下一阶段。历史结论不被最新构建覆盖。

只有本阶段真正达标才写“通过”。未完成时写“进行中/未通过”，不得因时间、上下文或剩余预算结束而冒充验收。
